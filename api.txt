# Business Discovery API — Current Documentation

**Technology:** Node.js, Express.js, Prisma ORM, PostgreSQL (Neon), Google Places, Gemini, Tavily, and Cloudinary.

**Status:** Working documentation based on the routes and implementation details available so far. Endpoints marked *Verify* should be checked against the current route files before being treated as final.

---

## 1. Base URL and conventions

For local development, the base URL is typically:

`http://localhost:3000`

Replace this with your deployed backend URL when using production.

- Request/response format: JSON, except where an endpoint returns CSV or a PDF redirect.
- Database: PostgreSQL accessed through Prisma.
- Business IDs and report IDs are generated by the database.
- Do not assume authentication is required; authentication requirements have not been confirmed for these endpoints.

## 5. Business discovery

### `GET /api/businesses`

Discovers businesses using the configured Google Places integration, checks existing database records/cache, and saves eligible results.

**Query parameters**

| Parameter | Required | Description |
|---|---|---|
| `city` | Yes | Target city |
| `category` | No | A specific category or `all` for all configured categories |

**Example**

```http
GET /api/businesses?city=Panchkula&category=Software%20and%20IT%20companies
```

**Example: all configured categories**

```http
GET /api/businesses?city=Panchkula&category=all
```

**Behavior documented so far**

- Checks existing cached records by city and searched category.
- Fetches missing data through the Google Places integration.
- Deduplicates and saves business records.
- Tracks cache hits, fetched categories, and failed categories.
- Supports CSV output in the discovery flow.

**Important:** The exact response content type, CSV columns, diagnostic header names, and error payloads should be verified against the current controller/exporter. Do not assume this endpoint returns JSON if the active implementation returns a CSV download.

## 6. Search and paginate saved businesses

### `GET /api/businesses/db`

Reads existing database records for the dashboard. This is the endpoint to use for searching and browsing saved businesses without triggering new discovery.

**Query parameters**

| Parameter | Required | Description |
|---|---|---|
| `search` | No | Search term |
| `city` | No | Filter by city |
| `category` | No | Filter by category; `all` means no category filter |
| `website` | No | Website filter; `all` means no website restriction |
| `page` | No | Page number; dashboard uses `1` as the first page |
| `limit` | No | Number of records per page; dashboard currently uses `50` |

**Example**

```http
GET /api/businesses/db?city=Panchkula&category=Software%20and%20IT%20companies&website=missing&page=1&limit=50
```

**Example response structure**

```json
{
  "success": true,
  "total": 120,
  "page": 1,
  "limit": 50,
  "totalPages": 3,
  "businesses": [
    {
      "id": "BUSINESS_ID",
      "name": "Example Business",
      "city": "Panchkula",
      "category": "Software and IT companies",
      "website": null
    }
  ]
}
```

This example is illustrative; the actual business objects may include additional fields and related report/research information.

**Pagination behavior**

- `page=1&limit=50` requests the first 50 matching records.
- `page=2&limit=50` requests the next page.
- `total` should represent the total number of matching records, not just the current page.
- `totalPages` indicates the number of pages available.

The React dashboard uses this endpoint for its database search, filters, and Previous/Next controls.

## 7. Retrieve a single business

### `GET /api/businesses/:id`

Retrieves one saved business by its database ID.

**Example**

```http
GET /api/businesses/BUSINESS_ID
```

The implementation has been described as returning the business with related reports and agent research records, with the newest related records available to the dashboard.

**Expected response shape**

```json
{
  "success": true,
  "business": {
    "id": "BUSINESS_ID",
    "name": "Example Business",
    "reports": [],
    "agentResearches": []
  }
}
```

This is a simplified response illustration, not the complete Prisma result.

**Errors to verify:** invalid or unknown ID, and internal database errors.

## 9. Audit: inspect a business website

### `GET /api/audits/businesses/:id/inspect`

Runs the website inspection flow for a saved business.

**Example**

```http
GET /api/audits/businesses/BUSINESS_ID/inspect
```

**Known inspection constraints**

- HTTP and HTTPS websites only.
- Public IP validation to reduce access to private/internal network addresses.
- Maximum of 8 pages in the crawl.
- Maximum HTML response size of 2 MB.
- Approximately 12 seconds timeout.
- Redirect limits are configured in the inspector.

**Response structure previously observed**

```json
{
  "business": {},
  "inspection": {}
}
```

The actual `inspection` object contains the inspector's findings; its full schema should be documented from the current implementation.

## 10. Audit: generate analysis and PDF report

### `POST /api/audits/businesses/:id/analyze`

Starts the business audit/report workflow for a saved business.

**Example**

```http
POST /api/audits/businesses/BUSINESS_ID/analyze
```

A JSON request body has not been confirmed as required for the route; the business ID is supplied through the path.

**Known workflow**

1. Creates a report record with a pending status.
2. Inspects the business website when applicable.
3. Runs AI analysis on the available business and inspection information.
4. Saves the analysis in the report's `reportData`.
5. Generates a PDF.
6. Uploads the PDF to Cloudinary.
7. Saves the PDF URL and final status to the report record.

**Example success response**

```json
{
  "success": true,
  "message": "Business audit and PDF generated successfully",
  "businessId": "BUSINESS_ID",
  "reportId": "REPORT_ID",
  "reportStatus": "COMPLETED",
  "inspectionStatus": "completed",
  "pdfUrl": "https://example.com/report.pdf",
  "analysis": {}
}
```

The URL and analysis are illustrative. Actual response fields may differ slightly depending on the latest controller.

**Report status values**

- `PENDING`
- `COMPLETED`
- `FAILED`

The exact response behavior for businesses without websites needs to be verified. Such businesses may need a new-website brief rather than a normal existing-website audit.

These routes have been described in earlier implementation discussions. Verify that they are still mounted at these paths.

### `GET /api/businesses/:businessId/reports`

Lists reports associated with a business.

**Query parameters**

| Parameter | Default | Description |
|---|---:|---|

| `limit` | `10` | Results per page; previously configured maximum `100` |

**Example**

```http

```

### `GET /api/reports/:reportId`

Retrieves a report and its associated business.

**Example**

```http
GET /api/reports/REPORT_ID
```

### `GET /api/reports/:reportId/pdf`

Redirects to the stored PDF URL when one is available.

**Example**

```http
GET /api/reports/REPORT_ID/pdf
```

**Known behavior described previously**

- HTTP `302` redirect when the PDF URL is available.
- HTTP `409` when the PDF is not available.

Confirm these details against the active report routes before publishing them as final.

## 12. Business research endpoints

The application mounts a research router under `/api/research`, and the research controller has been described as supporting:

- Running research for a business ID.
- Saving an `AgentResearch` record.
- Returning a completed research result or a failure.
- Retrieving a research record by its research ID.

The exact URL suffixes are not verified in the available information, so they are intentionally not invented here.

**Known research data fields**

- `businessId`
- `status`
- `websiteExists`
- `researchData`
- `error`

A successful research operation previously returned fields such as `researchId`, `businessId`, `status`, `websiteExists`, and `websitePath`. The exact full response schema must be checked in the research controller.
